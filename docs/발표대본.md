## 1. 표지 — 10초

안녕하세요. finaci는 여러 통화의 생활비 흐름을 계획하는 앱입니다. 이번에는 이미 입력한 예정 수입과 지출을 미래 계획에서 다시 확인하는 경험에 집중했습니다.

## 2. 목차 — 5초

Wallet 분석, 개선 결정, Flutter 구현 순서로 설명하고 마지막에 화면을 시연하겠습니다.

## 3. 앱 소개 — 15초

finaci는 여러 국가와 통화의 돈을 관리하는 사람을 위한 앱입니다. 베트남 급여, 한국 아르바이트 급여와 가족 지원금을 함께 고려하는 제 상황을 이번 사례로 삼았습니다. 학비는 목표의 한 예시입니다.

## 4. 현행에서 v2로 — 15초

Wallet에는 이미 다중 통화 계좌, 예정 결제, 예산과 통계가 있습니다. 계좌별 잔액과 중앙 플러스의 빠른 기록은 가져오고 싶은 강점이었습니다. finaci는 이 구조를 바탕으로, 등록한 예정 항목을 날짜별 전망과 연결하는 흐름을 제안했습니다.

## 5. 리뷰 근거 — 30초

공개 리뷰 20개를 날짜, 별점, 지역과 플랫폼별로 정리했습니다. 연결·동기화 불만 외에 수동 입력 부담, 중요한 잔액 표시와 선택의 복잡성에 대한 의견도 있었습니다. Google Play Phone 별점 분포는 원본 캡처를 남겼습니다. Apple과 Android 수치를 합치지 않았고, 오래된 리뷰가 현재 iOS 문제를 증명한다고 보지 않았습니다.

## 6. 저니와 원인 — 30초

Wallet의 여섯 flow를 따로 사용한 뒤 기본 순서로 저니를 구성했습니다. 리뷰 불만은 Sync에 많이 모였습니다. 제 과업에서는 Planned Payments와 Outlook을 연결하려고 다시 입력하는 부분이 어려웠습니다. 제휴보다 UI로 개선할 수 있는 이 지점을 골랐고, 원인은 입력 항목에서 전망까지 연결을 알아보기 어렵다는 UX 가설로 정리했습니다.

## 7. 화면 계획 — 60초

A는 실제 잔액을 먼저, 날짜별 예상 흐름을 다음에 보여 줍니다. 아래에는 전망에 반영한 예정 항목을 두어 숫자의 근거를 바로 찾게 했습니다. B는 같은 항목을 날짜, 이름, 통화 금액 순서로 보여 줍니다. 이 부분은 반복 입력을 줄이는 P07과 기억보다 알아보게 하는 P06을 적용했습니다.

목표가 있는 이번 사례에서는 기본 기간을 목표일까지로 두었습니다. 7일과 30일 탭도 남겼고, 목표 카드는 보조 정보로 배치했습니다. 각 요소는 번호, Flutter 위젯명과 업무명으로 가이드에 연결했습니다. 바뀌는 데이터와 표시 위치는 STATE 주석으로 적었으며, 실제 저장이나 앱 전체 상태관리는 넣지 않았습니다.

## 8. 셀프 논증 — 60초

처음 반론은 Sync 불만이 더 많으니 그 문제를 먼저 해결해야 한다는 것이었습니다. 저는 국가와 은행 제휴 범위를 이번 UI로 해결하기 어렵고, 직접 겪은 입력 반복을 설명하는 편이 과제 범위에 맞다고 판단했습니다.

기본 기간도 30일안에서 목표일까지로 수정했습니다. 다만 긴 전망은 확정된 돈처럼 보일 위험이 있습니다. 그래서 예상이라는 라벨만 두는 안을 보완했습니다. 현재와 예상을 분리하고, 고정 예시 전망이라는 표시와 포함·제외 항목을 가까이 두었습니다. 급여가 목표일 뒤로 늦어지는 사례도 준비했습니다. 새 판단을 보조자가 작성한 부분은 기록에 표시했고, 과거 제 발언으로 만들지 않았습니다.

## 9. Flutter 기술 — 45초

구현은 수업의 UI 전용 범위를 따랐습니다. A에서 B는 Navigator, 기간 전환은 TabBar, C와 D는 BottomSheet입니다. 데이터 요청은 api.dart에 모았고 json-server에서 GET만 합니다. FutureBuilder로 로딩, 오류, 빈 결과와 데이터 화면을 나눴습니다. 오류에는 다시 시도를 둡니다.

넓이는 LayoutBuilder로 읽어 휴대폰에서는 한 열, 넓은 화면에서는 정보를 나란히 배치합니다. 선택 표시만 setState로 바꾸며, 환율 변환이나 잔액 계산, AI 호출과 영구 저장은 구현하지 않았습니다. 화면의 전망과 응답은 미리 작성한 예시입니다.

## 10. 데모 — 75초

**조작 0–15초:** A의 계좌와 현재/예상을 보여 준다.

여기는 KRW와 VND 예시 계좌입니다. 현재 잔액과 고정 예시 전망을 구분했고 기준일과 환산 가정을 표시했습니다.

**조작 15–30초:** B로 이동해 목표일까지 탭과 예정 항목, 수입/지출 필터를 보여 준다.

같은 예정 항목을 일정에서 확인합니다. 새 입력 없이 날짜와 통화, 어떤 항목이 전망에 반영되는지 볼 수 있게 한 설계입니다. 이 데모가 실제로 거래를 저장하고 재사용하는 것은 아닙니다.

**조작 30–45초:** C를 연다.

2월 25일 급여가 7일 늦어 3월 4일에 들어오는 예시입니다. 그러면 2월 28일 기준으로는 급여가 빠진 전망을 비교하게 됩니다. 두 값 모두 사전 작성한 결과입니다.

**조작 45–55초:** C를 닫고 중앙 +로 D를 연 뒤 확인한다.

어느 주요 화면에서도 같은 빠른 기록 폼을 엽니다. 확인하면 실제 저장하지 않았다는 안내가 나옵니다.

**조작 55–70초:** 준비한 loading/error/empty 실행 화면이나 해당 상태 빌드를 보여 준다.

데이터를 기다리는 상태, 오류와 재시도, 데이터가 없는 상태도 구분했습니다. 실제 실행 캡처는 부록에 있습니다.

**조작 70–75초:** 넓은 화면으로 전환한다.

같은 정보를 넓은 화면에서는 두 열로 배치합니다. 여기까지가 UI prototype 범위입니다.

> 데모 화면을 미리 열어 둔다. 배포 URL은 실제 접속이 검증된 뒤 README의 최종 링크를 사용한다. 배포나 녹화가 끝나기 전에는 시연 완료로 기록하지 않는다.

## 11. 배움 — 15초

이번 과제에서 기록을 모으는 것과 계획으로 읽게 하는 것은 다른 문제라고 배웠습니다. 다음에는 실제 사용자가 예상 잔액을 보장 금액으로 읽지 않는지, 반영 항목을 쉽게 설명할 수 있는지 확인하겠습니다. 감사합니다.
